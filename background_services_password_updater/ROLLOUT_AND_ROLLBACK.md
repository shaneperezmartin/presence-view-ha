# Required approval and runbook

This is a plan, not permission to execute it. Preparation approval does not authorize publication, installation, live source inspection with expanded access, network/security changes, controls changes, enrollment, or an update/restart.

## Blockers before scheduling

1. Verify a supported Tailscale Serve HTTPS-only/no-Funnel route, exact hostname/certificate, installed Serve provenance, actual three-hop ingress chain, Core peer, and intended tailnet audience/ACL. A plain HTTP route cannot accept the password. No production route values are included here. Any new network/security configuration or HA restart requires separately disclosed action-time approval.
2. Verify the exact currently installed 0.2.6 source hashes/modes, actual source config, and metadata-only extra-file inventory using a separately authorized read mechanism. Packaged baseline equality has not been established on live. Stop on any difference; this bundle must not learn or overwrite a new baseline. Only the exact historical two-field private variant can use this compatible transaction, and only with a prior independently verified private baseline pin. Obtain that pin from the retained installation record, not from a current mismatch. Keep it out of repository/chat/logs. Saved Supervisor options are preserved, not converted to public defaults.
3. Complete an actual image build and permitted synthetic HA/iPhone acceptance for the route, session cookies, setup approval UX, wrong-password limit, lock/expiry, back navigation, tabs, interrupted downloads and preserved controls/data. The existing helper/unit tests are not substitutes.
4. Establish a protected backup/recovery mechanism for exact source, current saved options/control states, and required data. App/system backups exclude archive/model/tmp paths and are not complete audio backups. Keep all private copies private and outside generic/public packages. Do not create credentials as part of source preparation.

5. Before any cutover, establish and verify a supported original-app installed-image recovery route back to 0.2.6, preserving identity, options and data. Tested source rollback does not prove that HA permits an installed-image downgrade. Do not proceed to 0.2.7 until that recovery mechanism is verified; do not leave this discovery until after a failure. Any needed rebuild/reinstall, alternate recovery tool or backup restore remains outside this plan and requires its own explicit authorization.

## Concrete approval scope

Immediately before live changes, obtain explicit authorization identifying the repository/branch and exact public files if publication is wanted; the temporary helper installation, whole-local-apps write mount/security grant, execution and later removal; the app-only update/restart and password boundary; the short BOTH-controls pause/drain/restore window; and rollback to 0.2.6 if the cutover fails. Disclose that rollback removes the independent app password boundary, old bearer exports stop working in 0.2.7, and HA MQTT controls remain available outside that lock. There is no approval to rebuild/reinstall the original app, change its slug, grant broad HA APIs, reset passwords, or restore all of HA.

Installation of this helper entails the broad `local_apps` read-write mount even in inspect mode. Its code narrows the target but the mount does not. The concrete security grant requires action-time confirmation. The helper has no exposed port, host networking, HA/Supervisor API, audio or target data mount. No privileged/full-access flag is requested.

## Approved cutover sequence

1. Immediately before cutover, record original recording AND transcription switch states, current active/process status, saved option values privately, archive counts/metadata, source identity/hashes/modes, exact extra-file metadata, and backup verification. Do not rely on an older snapshot. Keep private values out of logs/chat/public artifacts.
2. Turn BOTH recording and transcription controls off through the authorized original controls. Turning off recording alone is insufficient because transcription can keep capture running. Allow capture closure/flush.
3. Prove work has drained, not merely waited a fixed interval: both desired controls and active flags off, `capture_process_running=false`, queue length zero, diarization `pending_files=0` and `processing=false`, model/setup work idle. Queue length zero alone excludes in-flight Whisper processing and is insufficient. Use metadata-only transcript file listings across both floors and all pages to verify no files remain active/in-flight. If the supported diagnostics cannot prove this, stop and report the gap. Do not bypass a denied status route.
4. Stop only the original app after those checks. Its approximately 20-second shutdown queue wait may cancel work; graceful stop is not itself proof of drain. Reconfirm stopped state and source/control snapshot.
5. With the separately authorized helper installed, use `diagnose` only if needed for bounded extra-file metadata, then `inspect` with the reviewed exact `preserve_extra_files` list. Privately supply the independently recorded historical baseline pin when preserving the recognized two-field source-default variant; keep this same pin for all later inspect/apply/rollback operations. Inspect must report private_pin_verified=true and historical_defaults_preserved=true for that variant. Any other source mismatch or unknown extra is a blocker. No arbitrary hash override, file deletion, mode normalization, or relaxed allowlist is allowed.
6. After all preconditions and authorizations are satisfied, set `mode=apply`, use the freshly returned exact source fingerprint and set both `maintenance_confirmed=true` and `rollback_security_loss_confirmed=true`. These do not replace the external checks or owner approval. Run once. Verify result and a new inspect. If refused or interrupted, preserve source/recovery files and use the recovery procedure; do not continue an app update with mixed source.
7. Use the original app's normal Update flow, not Rebuild or uninstall/reinstall. Preserve installed slug, saved original options, devices/entities/MQTT identities, data and retention. Configure only separately approved verified route/enrollment approval values via the normal private administrator UI. No password/setup code goes through chat or into an ordinary option. If credentials/options/route state differ materially from the agreed scope, stop.
8. Verify 0.2.7 health, HTTPS boundary, no HTTP/forged-chain bypass, owner-completed iPhone enrollment, subsequent login/logout/expiry, original saved options/data/archive preservation and unchanged MQTT identities. A fresh setup is not automatically logged in. Do not claim success merely because the version changed.
9. Restore BOTH original control selections only after success or authorized verified rollback. If originals were ON/ON, restore both ON and verify both desired/active states, capture and transcription output. Do not infer success from switch state alone. If acceptance fails or restore is unsafe, report that the controls remain paused rather than enabling silently.
10. Stop and remove the temporary helper under the same approved rollout scope. Preserve protected recovery data until the user authorizes its deletion; helper removal must not delete original app data or private extras. Verify helper write access is gone and original app remains installed/running.

## Recovery / rollback

- Before update/restart: a normal recoverable apply error automatically restores verified baseline source. A crash may leave mixed source; inspect with this exact bundle, the same independently recorded private pin and extras list, then use the freshly fingerprinted authorized recovery. Mixed-state apply is deliberately a rollback. Never run original app code while source is mixed.
- For explicit rollback, obtain current confirmation that reverting to 0.2.6 removes the independent app web-password boundary and may re-enable old bearer behavior according to preserved existing settings. Pause BOTH controls, prove drain, stop only the app, preserve current state, inspect, then `mode=rollback` with both attestations true and the fresh fingerprint. The helper only restores exact saved source/config and removes its added source files by preserving them in recovery storage.
- Use the supported original-app update/recovery route for the restored 0.2.6 source only after confirming that HA accepts that recovery. Versioned Supervisor source establishes that normal Update can target a different lower store version, while Rebuild rejects installed/store version differences. Actual image recovery has not been exercised here: verify the restored store version and build feasibility before cutover. Do not use a standard app-backup restore as a shortcut because excluded archive/model data may be removed during restore. If unavailable, stop for an authorized supported recovery plan rather than reinstalling or restoring all of HA.
- Verify exact baseline hashes/modes, private extras, saved options, archive/data and MQTT identities; restart only the app and restore the original control states. Existing `/data/app-password.json` is neither read nor deleted by source rollback. Reapplying the password candidate would use that state again; any password-state removal/reset is separately authorized administrator work.
- If unknown edits, replaced directories, changed private extras or corrupt backups are detected, automatic recovery refuses. Preserve every recovery object and conflicting inode; request exact reconciliation authorization. Do not force, rebaseline, purge or restore a whole system backup as a shortcut.
